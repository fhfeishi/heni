# TypeScript：产品文案与事实数据的边界

## 问题

界面上出现 `SQLITE`、`FFPROBE` 或 `ACTIVE PLAYBACK SESSION`，是把实现细节当成了产品语言。
但把所有英文都删掉也不对：FLAC、H.264、Hz 和 kbps 是用户需要的媒体事实。

## 直白模型

先区分三类内容：产品标签、来源数据和纯装饰。产品标签使用简明中文；曲名、路径、编码、
标签与测量值保留事实；占位唱片不承载品牌或媒体信息，并从可访问树隐藏。

`MediaDetailsPanel` 的 `streamKindLabels` 使用
`Readonly<Record<MediaDetails["streams"][number]["kind"], string>>`：

- `MediaDetails["streams"]` 取得契约中的流列表类型；
- `[number]` 取得一个列表元素的类型；
- `["kind"]` 取得 `audio | video | unknown` 联合；
- `Record` 要求每一个合法分支都有文案，`Readonly` 禁止修改映射。

未来增加一种流类型时，遗漏中文标签会成为编译错误，而不是运行后显示 `undefined`。
这里没有增加一个需要人工保持同步的 `string` key 列表，也没有无依据的类型断言。

## 最终选择

让文案留在所属视图中；对有限状态使用穷举映射。不修改已经验证的 IPC 与持久化字段。
唱片使用现有 CSS token 和渐变，主播放台、底部播放条、MiniPlayer 都不再显示单字母 H。
没有新增翻译框架、全局文案 store、图片下载或品牌资源管理器。

## 替代方案与取舍

当真正支持第二种语言、运行时语言切换或翻译流程时，再建立集中词条目录。现在只有中文
产品界面，提前加入完整国际化体系会增加维护成本，不能直接解决术语泄漏与信息层级问题。
CSS 唱片只是中性占位，并不代表已经支持真实专辑封面或全景背景。

## 如何验证

App 测试切换四个工作区，检查固定工程标签不再出现，同时检查完整字标和无文字占位。
测试使用空夹具，不能用“禁止所有英文”的断言误伤用户曲名。媒体详情测试则专门证明
中文流类型与真实 FLAC/H.264、采样率、分辨率等信息可以共存。

组件测试无法证明文字是否被裁切。Windows 实机检查发现长空态标题在三栏下被省略，
因此把固定文案精简为“从一首歌开始”；真实长曲名继续遵守已有截断策略。
浏览器精确视口和 125%/150% DPI 检查仍是独立门槛。

## 阅读与练习

建议阅读 `src/features/library/MediaDetailsPanel.tsx`、对应测试、
`src/features/player/NowPlayingView.tsx` 和 `src/app/App.test.tsx`。

练习：给未知编码的流写一个断言，确认显示“未知编码”；再传入用户自定义英文曲名，
证明品牌/中文标签检查不会修改或禁止真实媒体数据。不要为了测试新增产品状态。
