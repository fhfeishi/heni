# TypeScript：减少界面信息，不删业务信息

## 问题

每个曲库行同时放标题、完整路径、编码参数和多组操作，会让曲库显得拥挤，却显示不了更多
音乐。简单地删掉路径又会损害同名文件辨认与错误恢复。

## 直白模型与最终选择

默认行只展示标题、类型和真实音频信息；用户打开“更多”时，展示可选择复制的完整路径与
次级操作。搜索仍使用原始 `LibraryItem.path`。这只是视图的渐进式展示，不修改 DTO、
SQLite、播放队列或文件本身。

`actionsOpen` 继续是每行的局部状态。全局保存展开状态或把它写入曲库没有用户收益。
长标题保持省略并提供完整 title；长路径在展开区域换行，不挤占操作按钮。

## 一个小类型问题

`codecName?.toUpperCase()` 在缺少编码时返回 `undefined`，不是 `null`。
只写 `.filter(value => value !== null)` 会保留这个空值，拼接后可能出现开头多余的分隔符。

这里改成类型守卫：`.filter((value): value is string => typeof value === "string")`。
过滤后的数组明确只包含字符串，随后 `join(" · ")` 不需要断言，也不会为未知编码伪造名称。

## 验证与替代方案

组件测试覆盖路径按需出现/收起、次级操作保持原参数、未知编码没有多余分隔符，以及待读取/
读取失败的文案。缺失文件仍保留主要“重新定位”操作与明确提示，不通过降低整行透明度隐藏。

如果未来性能数据证明大量曲库行成为瓶颈，再加入虚拟列表。当前先改善信息结构，不能把
安装虚拟列表依赖当成性能测量或视觉改善的替代品。

## 阅读与练习

阅读 `LibraryItemRow.tsx`、`LibraryItemRow.test.tsx`、`LibraryPanel.test.tsx` 和
`libraryProjection.ts`（均在 `src/features/library/`）。

练习：加入两个标题相同、路径不同的媒体，验证按路径搜索仍能准确筛选，并分别展开确认
来源。不要为“更短的显示路径”改写真实 `LibraryItem.path`。
