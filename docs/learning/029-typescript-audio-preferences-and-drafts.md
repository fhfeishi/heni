# 029 — 音量草稿、已提交状态和持久化失败

## 问题和直白模型

滑块显示 37%，不一定表示声音已经变成 37%。一次交互至少有“正在选择”“等待提交”“权威结果”三个时刻。把每个指针移动都当成已保存状态，会掩盖失败并造成重复写入。

本切片让 Rust 保存音量、静音、上次非零音量的一组值；React 只持有当前手势草稿。数据库在播放核心启动前读取，所以恢复静音不依赖界面加载速度。

## TypeScript 的职责

`PlaybackVolume` 的草稿是只读对象，带目标音量和开始时的 `baseVolume/baseMuted`。权威音量发生变化时草稿失效；正常位置更新或切歌不改变这两个字段，因此不会无故取消音量手势。这里不照搬 seek 的 generation：seek 属于某一首歌，音量属于整个播放器。

失效必须真正清掉草稿，而不只是暂时不显示。新增回归先证明：外部静音来回切换、数值返回起点后，旧目标会复活。现在在明确不匹配的条件下同步清掉当前组件草稿；下一次值回到起点也不会提交旧手势。连续按键和未提交就卸载同样有测试。

松开指针或键盘时提交一次，等待 Promise 结束再清理草稿。同步 ref 阻止 React 下次渲染之前的重复提交；局部 pending 保留可聚焦控件，`aria-busy`／`aria-disabled` 表达等待，事件 guard 真正阻止重入。仅设置 ARIA 不会自动禁用事件。

卸载时递增 lifecycle；旧 Promise 不能修改新界面的局部状态。取消、失焦和丢失捕获只放弃未提交草稿。返回失败后，滑块回到 snapshot，不伪装保存成功。

## 从 unknown 到可解释的错误

生产 snapshot 类型仍从 Zod 推导。新增 `preferencesError` 是可选字段：Rust 正常时省略，读取偏好失败时才附带结构化错误；不是 `null` 或随意字符串。有限错误码映射为中文产品文案，原始诊断不直接展示。

`usePlayback` 区分命令失败与读取失败：正常位置读取只说明“现在读得到了”，不能证明先前保存成功。因此保存命令的错误保持到用户关闭或下一次操作；启动恢复警告可以关闭，同一警告不会每 300ms 弹回。出错仍可使用静音的有效 snapshot，不把所有能力一同锁死。

## 最终选择和替代方案

本切片选择“先预览，松开才应用并保存”，没有引入第二个音量 store、写入队列或 debounce 工具库。它与 Flutter 的拖动中实时试听存在未关闭差异。若之后实现实时试听，应先定义预览取消、立即退出、写入失败和 Mini 同步行为，而不是直接给每次 `onChange` 加一次异步写库。

Rust 事务测试、假引擎和组件测试各自只证明所属边界；真实 Release 重启和声音听感仍需分别留证。详见 ADR 0005。

练习：让音量保持 37%，在一次拖动草稿中接收同曲正常位置更新，再接收来自其他控制入口的静音变化。分别断言草稿保持与失效，并证明无效手势不会写入 0%。解释为什么这里不能只比较 generation。
