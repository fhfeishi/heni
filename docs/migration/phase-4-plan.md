# Phase 4：产品 UI 与 Windows 交互

状态：4A–4G 核心竖切与首轮收口完成  
更新日期：2026-09-02

## 4A 前的 UI 判断

当前 Tauri 界面是 Phase 1–3 的 walking skeleton：它能把播放、队列、曲库、歌单、迁移和媒体详情全部暴露出来，便于自动测试和检查状态，但不是产品设计目标，也不满足 Flutter v1 的主要体验等价。

主要问题不是某个颜色或按钮，而是信息架构：

- 当前播放、队列、曲库、歌单和控制条全部纵向堆叠，窗口没有清晰的主任务；
- 顶栏展示技术栈和运行时连接信息，像调试页面而不是播放器；
- 播放控制位于长页面底部，浏览曲库时可能离开视野；
- 曲库行把常用、次要和诊断操作并列，信息密度和优先级失衡；
- 歌单是独立的大型编辑表单，没有融入侧栏与主内容区；
- 没有统一的应用框架、导航、详情抽屉、空状态和响应式规则；
- 当前紫色卡片只是临时 token，没有实现旧版已经批准的主题/美景体系；
- `App.tsx` 已同时承担装配、视图组合和多组操作回调，继续直接添加 UI 会形成新的超大页面。

因此 4A 没有在原纵向页面上反复“美化”，而是先重构应用框架和视图边界，再把已经通过测试的功能迁入互斥主视图。

## 4A 实施结果

4A 已建立 `AppFrame → TopBar/Sidebar/MainView/PlaybackBar` 骨架，并交付以下行为：

- `AppView` 使用四成员字符串联合类型，视图切换只保存在 React 局部状态；
- 正在播放、曲库、歌单和队列一次只展示一个主视图；
- 浏览导航不会发送 playback command，选择或播放媒体后才进入正在播放视图；
- 播放条在所有主视图常驻，队列入口、上一首、播放/暂停、下一首、停止、静音和音量均保留；
- 侧栏计数与固定的无障碍名称分离，避免“曲库0”一类不稳定名称；
- 原技术栈横幅已移除，运行时连接仅保留为非阻塞状态；
- CSS 使用录音室哑光/深度染色基础 token，900px 时收窄侧栏，不引入组件库或第二套领域状态。

首轮视觉证据：

- 1180×760：document、AppFrame 均为 1180×760，无页面级滚动；主内容 960×584；
- 900×620：document、AppFrame 均为 900×620，无页面级滚动；侧栏 84px；主内容 816×444，只允许主内容按需独立纵向滚动；
- 1180px 初检发现下一首卡片导致空状态主标题截断，已在 1240px 以下隐藏次要卡片，复核标题 `clientWidth === scrollWidth`；
- 最低尺寸下实测曲库/正在播放互斥，播放条继续可见；普通浏览器没有 Tauri bridge，因而本地调用失败提示不计作桌面功能回归。

自动证据为 14 个 TypeScript 测试文件、48 项测试全部通过；其中 App 层新增“主视图互斥、导航不触发播放、播放条跨视图常驻”契约测试。

## 视觉与产品基线

沿用 Flutter v1 已批准且仍符合 local-first 定位的方向，但 clean-room 重写 React 组件：

- `录音室哑光`：低眩光、信息优先、长时间使用稳定；
- `深度染色`：主题色只作为环境染色、选中状态和关键控制，不把高饱和色铺在正文后；
- `播放控制台`：当前媒体、真实音频属性、下一首和本地文件操作形成明确层级；
- 单一全窗口美景层，曲库/歌单加强遮罩，播放页适度展示图像；
- 不恢复歌词、在线内容、音频导出或无真实依据的“无损”标签；
- 中文为主，字体栈优先 Microsoft YaHei UI / Segoe UI；
- 没有真实价值时不引入大型组件库或通用设计系统框架。

## 目标信息架构

```text
AppFrame
├─ TopBar                品牌、当前视图标题、视图相关主操作、窗口控制
├─ Workspace
│  ├─ Sidebar            曲库、当前队列、歌单入口和数量
│  └─ MainView
│     ├─ NowPlayingView  播放控制台
│     ├─ LibraryView     搜索/筛选/列表/批量操作
│     ├─ PlaylistView    歌单浏览与编辑
│     └─ QueueView       活动队列、定位、移除，后续加入重排
├─ PlaybackBar           始终可见的当前曲目、进度、主控制、音量
└─ OverlayLayer          媒体详情抽屉、确认对话框、轻量状态提示
```

活动播放队列和 SQLite 曲库仍分别由现有 Rust runtime/repository 掌握。切换视图只改变 TypeScript 局部 UI 状态，不能重新载入媒体或修改播放队列。

## 分片计划

### 4A：应用框架与导航

目标：消除所有功能纵向堆叠，建立稳定的顶栏、侧栏、主视图和底部播放条。

- 定义直白的 `AppView = "now-playing" | "library" | "playlists" | "queue"`；
- 把 `App.tsx` 缩回依赖装配与用例协调，拆出 `AppFrame`、`Sidebar`、`NowPlayingView`、`QueueView` 和 `PlaybackBar`；
- 迁移现有功能，不改变 Rust command、snapshot 或 repository 语义；
- 当前曲目切换、选择文件自动播放后进入播放视图；
- 浏览曲库/歌单不改变播放状态；
- 底部播放条在所有视图可见；
- 移除面向最终用户的技术栈标题，把连接异常保留为非阻塞状态。

验收：1180×760 和 900×620 不产生页面级纵向/横向溢出；四个主视图可键盘切换；现有播放/曲库/歌单测试语义保持通过。

状态：竖切完成。浏览器尺寸、语义按钮和自动测试已通过；真实 Windows DPI/键盘 E2E 继续留在 4G/Phase 5。

### 4B：播放控制台与持久播放条

- 当前媒体封面或 Heni 唱片 fallback；
- 标题、路径、播放状态和已索引的真实 codec/采样率/声道信息；
- 下一首预览和打开详情入口；
- 播放条按实际宽度切换 wide/compact 进度布局；
- 静音恢复、上一首/播放暂停/下一首、队列入口形成明确主次；
- 不声称 bit-perfect，不把估算码率显示为精确值。

验收：空队列、已暂停、播放中、已完成、错误和未知时长均有稳定布局；控制条不会因长标题、中文路径或时间文本挤压滑块。

状态：核心竖切完成。已交付 Heni 唱片 fallback、真实快速元数据、下一首预览、当前媒体按需详情抽屉、跨视图播放条和 960px compact 规则。播放状态文案、未知时长、长标题、播放/暂停和 generation 切换时的 seek 草稿均有组件测试。浏览器实测 900×620 时隐藏时间标签并给滑块 391px，1180×760 时恢复双时间列；两档播放条 `scrollWidth === clientWidth` 且页面无整体溢出。真实媒体/DPI/错误恢复视觉 E2E 继续留在 4G/Phase 5。

### 4C：曲库工作区

- 搜索、媒体类型、可用状态和基础排序使用可测试的 TypeScript 纯函数；
- 行内只保留播放主操作，下一首/入队/详情进入可访问的次级菜单或详情抽屉；
- 扫描进度、取消、缺失文件和旧数据导入成为上下文状态，不占据每次浏览的主视觉；
- 媒体详情从行内大块内容迁入右侧抽屉；
- 数据量证明需要时才加入虚拟列表，不预先引入库。

验收：1、100、5,000 项投影测试；长路径/中文标题无横向溢出；搜索不修改 SQLite 和播放队列。

状态：核心竖切完成。搜索覆盖标题、路径和 codec，类型/可用性筛选与标题排序均为只读 TypeScript 投影；输入值用显式收窄函数处理，不以类型断言跳过建模。列表只保留“播放”为主操作，详情/下一首/入队通过带稳定 aria 名称的次级操作披露；详情复用 4B 抽屉。1、100、5,000 项投影和不修改输入顺序已有测试，组件测试验证筛选不调用导入、播放或详情回调。

900×620 数据夹具实测 36 项、长中文标题/路径、音频、视频和缺失文件：document 900/900、工具栏 755/755、首行 755/755、曲目文案区 597/597，均无水平溢出；主内容只产生预期的独立纵向滚动。筛选到 6 个视频并展开次级操作后，document/main/row 仍无水平溢出。视觉夹具位于 `fixtures/visual/library-workspace.html`，不进入正式入口或连接 SQLite。

### 4D：歌单与活动队列

- 歌单入口进入侧栏，主区分为歌单标题、曲目列表和编辑操作；
- 新建、改名、说明、删除和批量成员操作保持现有事务语义；
- 活动队列是独立视图/抽屉，突出当前项、下一首和移除；
- 增加队列定位、搜索、确认清理；最后才实现拖拽重排和 Rust 权威重排命令。

验收：浏览歌单、切换歌单、搜索和编辑都不打断当前播放；重排加入后用共享 fixture 验证 current index 不漂移。

状态：核心竖切完成。歌单主区改为“摘要与成员浏览优先、元数据按需编辑”，成员与曲库候选拥有独立本地搜索；新建、保存、批量加入/移除继续复用既有 Hook 和 Rust 事务，删除增加不会触碰曲库文件的二次确认。缺失成员引用仍显示并可移除，不因投影被静默丢弃。

队列新增标题/路径搜索、当前项定位、当前/下一首强调和清空二次确认。`projectQueueRows` 在筛选后保留 Rust 权威 `queueIndex`，播放和移除不会误用可见行下标；清空确认绑定打开时的 `generation:sequence`，snapshot 变化后旧确认自然失效。浏览、切换与搜索均为 React 局部状态，App 组件测试确认不会发送 playback command。

队列重排最终通过共享 `reorder-queue { fromIndex, toIndex }` command 落在 Rust 权威 session。移动当前项或其他项跨越当前项时，会重新计算 current index，但保持当前媒体、generation、position、duration 和 status；controller 不重新加载音频，只增加 sequence。React 提供拖放及带稳定 aria 名称的上移/下移按钮，两种入口共用同一命令；拖动绑定开始时的 `generation:sequence`，陈旧 drop 被丢弃，搜索状态下因隐藏项位置含义不明确而禁用重排。

该切片完成时相关测试全部通过；4G 收口后的当前门禁为 28 个 TypeScript 测试文件、92 项测试和 61 项 Rust 常规测试。`fixtures/visual/session-workspaces.html` 使用 60 项曲库、8 个歌单和 24 项队列，在 1180×760、900×620 实测 document、AppFrame、工具栏、重排控件与歌单工作区均无水平溢出；超长歌单名首轮发现的网格侵入已修正，左右列复核保持 16px 间隔；队列搜索/定位/重排入口、歌单切换、编辑和删除确认均在浏览器实际操作通过，控制台无告警。

### 4E：主题、美景与动效

- 建立少量语义 token：matte/surface/raised/text/accent/danger/focus；
- 单一根背景层，图片缺失时回退主题渐变；
- 曲库/歌单与播放视图使用不同但受约束的遮罩强度；
- 主题切换 280–420ms，hover 140–220ms，无持续漂浮或脉冲；
- 美景来源、持久化与权限在真实用例出现时再接 Rust/SQLite。

验收：每个主题在 1180×760、900×620、125%/150% DPI 保持可读；关键文本和焦点状态达到可接受对比度。

状态：核心主题与背景竖切完成，真实图片来源和设置持久化待真实用例。没有照搬 Flutter 的 14 套 palette，而是先保留录音室、深夜、潮汐 3 套语义明确的暗色主题；主题目录用 `as const` 推导 `HeniThemeId`，DOM/未来存储值必须经 `parseHeniThemeId` 收窄。主题状态留在 React 外壳，不进入 playback snapshot，也不触发 playback port。

`SceneryBackdrop` 成为唯一根背景层，始终保留主题渐变；可选图片区分 fallback/loading/ready/failed，加载失败只回退渐变。播放模式使用较轻遮罩，曲库/歌单/队列使用更强遮罩。主题入场 360ms、按钮反馈 180ms，并由 `prefers-reduced-motion` 压缩为近乎即时；没有持续漂浮或脉冲动画。文件来源、授权与重启持久化没有在缺少正式 settings/image use case 时伪实现。

主题切片完成时相关自动测试全部通过；本阶段最终门禁见 4F。三套主题分别在 1180×760 与 900×620 实际切换，顶栏、队列、歌单双列、播放台和常驻播放条均无水平溢出；最小普通窗口顶栏为 900/900、歌单工作区 757/757。首轮潮汐截图发现唱片 fallback 和选中态仍含固定绿色，已改为语义 accent token 后复核；最终浏览器控制台无 error/warning。125%/150% Windows DPI、真实美景图片和对比度工具审计继续留在 4G/Phase 5。

### 4F：Windows 窗口体验与 MiniPlayer

- 在普通窗口内容稳定后再关闭原生标题栏；
- Tauri window facade 集中处理拖动、双击最大化、最小化、还原和关闭；
- 保留 Windows 边缘缩放、系统菜单、`Alt+F4`、DPI 和工作区最大化语义；
- 窗口几何持久化；
- MiniPlayer 使用同一 Rust playback session，只切换视图和窗口几何。

验收：真实 Windows E2E 覆盖窗口按钮、拖动区域冲突、900×620、MiniPlayer、重启恢复和多显示器基本场景。

状态：核心竖切与主要真实窗口路径完成，自定义标题栏、多显示器和 DPI 扩展矩阵仍待验收。`src/infrastructure/tauri/windowPort.ts` 是前端唯一窗口命令入口，所有 Rust 返回值先经过 Zod；`useWindowMode` 只持有局部视图状态，MiniPlayer 继续消费同一份 `PlaybackSnapshot` 和同一个 `PlaybackPort`，切换模式不会发送 playback command。

Rust 使用官方 `tauri-plugin-window-state` 负责主窗口跨重启的 size、position 和 maximized。插件的 filter 只在窗口就绪时求值，且后续会持续观察 resize/move，因此不能把它当作动态 MiniPlayer 隔离。Heni 在 `WindowRuntime` 内另存当前会话主窗口几何，再将客户区切到 420×236、最小 360×220、当前显示器工作区右下角并置顶；返回或收到 `CloseRequested` 时先恢复原位置、尺寸和最大化状态，再刷新插件持久化。启动 snapshot 还会把早期版本遗留的非法小窗主界面修复为 1180×760。负坐标副屏、小于目标小窗的工作区和主界面非法尺寸均有 Rust 纯函数测试。

浏览器首次切到 420×236 时发现 `html/body/#root` 仍保留 900×620 CSS 最小值，页面实际按 900×620 排版并裁切右侧控制；修正为依据 `data-window-mode` 切换根约束后，420×236 与 360×220 的 document、AppFrame、chrome 和 MiniPlayer 均严格等于视口且无水平/纵向整体溢出。播放/暂停、静音、返回主窗口和 900×620 约束恢复均实际操作通过，页面诊断无 error/warning。当前仍保留 `decorations: true`，因此系统菜单、边缘缩放和 `Alt+F4` 没有被自定义 chrome 冒险替换。

真实 Windows Release 首轮发现“React 已返回主界面、原生窗口仍停在 420×236”的插件缓存覆盖问题，上述 runtime 几何边界据此修正。复核覆盖三条路径：被旧状态污染后的首次启动自动恢复 1180×760；1180×760 → 420×236 → 主窗口恢复原位置和尺寸；MiniPlayer 中点原生关闭按钮后重新启动仍为完整 1180×760 主窗口。三条均通过。

### 4G：视觉与可访问性收口

- 固定 wide/medium/minimum 三档截图基线；
- 键盘顺序、可见焦点、aria 名称、dialog focus trap 和 reduced motion；
- 空、加载、错误、缺失文件和大量数据状态；
- Debug/Release 字体、图标、缩放与 GPU 表现；
- 把技术状态和诊断信息移到设置/关于或日志，不污染主界面。

状态：首轮收口完成，DPI/对比度和更完整错误矩阵继续作为 Phase 5 发布验收。媒体详情抽屉现在是带 `aria-modal` 的 dialog：挂载时接管焦点，支持 Esc 关闭和 Tab 边界，卸载时只在原触发控件仍存在时还原焦点。行为由独立组件测试覆盖，没有把 DOM 引用提升到 App 或全局 store。

900×620 顶栏复核为 `scrollWidth === clientWidth`；在 960px 以下收起重复的“主题”和运行时文字，同时让 combobox 保留“界面主题”、status 保留完整运行时 aria 名称。真实 Release 1180×760 与 MiniPlayer 的字体、图标、原生标题栏和空播放状态完成目视检查。Phase 5A 已在后续完成结构化中文错误提示、原始诊断隔离、恢复动作和缺失引用说明；125%/150% DPI、自动对比度、真实缺失文件触发和 GPU/长时表现仍未完成。

## 工程约束

- 不复制 Flutter widget 源码，不恢复 8,000 行页面结构；
- React 组件不直接 `invoke`，新 OS 行为继续走 typed port；
- 不把 Rust snapshot 复制成第二套全局 store；
- 视图状态局部保存，只有出现跨视图真实消费者时才提升；
- 每个分片先写行为/响应式测试，再调整视觉；
- 新图标优先使用仓库内受控 SVG 组件，避免仅为几个图标引入大型依赖；
- UI 改造不得降低播放、扫描、迁移和事务测试门槛。
